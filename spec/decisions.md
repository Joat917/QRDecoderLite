# 设计决策记录

每条只写三件事：决定什么、为什么、付出什么代价。大致按时间先后排列，实现细节看对应模块文档。

## 两个引擎并行，结果合并

决定：ML Kit 与 WeChatQRCode 同时执行，结果按文本去重后合并，ML Kit 的结果优先。

理由：两个引擎能力互补。ML Kit 覆盖一维码与多种二维码，微信引擎对难认的二维码识别率更高。

代价：单次解码的内存和耗时都接近两个引擎相加，APK 因为要打包 OpenCV 的原生库而明显变大。

## 单个引擎失败不算整体失败

决定：一侧失败、另一侧成功时用成功的一侧。

理由：早期规则是任一引擎失败即整体失败，结果是一个引擎读图失败就把另一侧已经认出的内容丢掉。

代价：引擎故障只出现在日志里，用户看不到。若两侧都失败才显示错误卡片。

## 引擎不丢弃缺位置点的结果

决定：位置点可以为空，文本一律保留，是否画多边形由界面决定。

理由：微信引擎对整张图直接解码时会拿到文本而没有位置点，早期实现把这类结果直接丢弃。

代价：界面上会出现没有标注框的卡片，需要用户理解「位置未知」的含义。

## 日志统一入口与固定前缀

决定：所有日志经 `util/AppLog` 输出，TAG 为 `QRLite/` 加组件名，消息写成阶段加键值对。

理由：原先各文件自定义 TAG 并直接调用系统日志接口，无法与系统日志和第三方库日志区分，出错时缺少输入信息。

代价：多一层包装，新增组件时要按约定取名字。详见 `spec/error-handling.md`。

## 用户看到的错误是真实原因

决定：错误文字用方括号加异常类名，后接异常自带描述；资源里的文字只在描述为空时使用。

理由：早期把异常换成「识别失败，请重试」这类句子，用户与开发者都拿不到任何可查信息。

代价：文字偏技术，长度不可控。

## 界面文字全部放资源文件

决定：按钮、提示、无障碍描述、错误说明都放 `res/values/strings.xml`。

理由：代码里散落中文字面量难以统一修改，也无法做多语言。

代价：取文字需要组合上下文，回调里只能传已解析好的字符串。

## 结果页接管返回键

决定：结果页用返回键处理器，操作栏打开时先关操作栏，否则回主界面。

理由：应用只有一个 Activity 且没有导航栈，页面不处理返回键时按下会直接退出应用。

代价：主界面不接管返回键，在主界面按返回直接退出应用，这是有意的。

## 引擎读图只打开一次文件

决定：微信引擎读图时把文件内容一次读进内存，再解码两次。

理由：有的图片来源只能读到一次数据流，打开第二次会失败；ML Kit 只读一次，所以不受影响。

代价：文件内容会在内存里多留一份。后续若支持超大图片，应改为写临时文件再解码。

## 测试只保留可离线运行的纯逻辑

决定：需要在单元测试里断言 Android 框架返回值的用例一律删除或移入设备测试。

理由：这类断言在 JVM 上只能拿到默认值，测试长期失败，反而掩盖真实回归。

代价：依赖 Android 行为的逻辑只能靠设备测试与手工清单覆盖。

## 混淆只保留 OpenCV 的字段名

决定：`app/proguard-rules.pro` 只为 `org.opencv` 保留字段名，更宽的两层规则写在注释里备用。

理由：OpenCV 的 Java 层由 JNI 按字段名访问，而该库不提供混淆规则。ML Kit、Coil、Compose 自带规则，不需要重复声明。

代价：混淆后的安装包只在调试版本上验证过，发布包一旦崩溃要用 `mapping.txt` 还原堆栈。

## 只接受单张图片分享

决定：只注册单张图片的分享入口，多张分享不注册。

理由：早期实现收到多张时只处理第一张，等于一半功能，且容易误以为支持多图。

代价：用户想一次识别多张时要逐张分享。

## 结果页状态不保存图片地址

决定：`DecodeUiState` 不存图片地址，图片归属由 `Sheet.Result` 记录。

理由：两处保存同一份地址，读取时要写兼容分支。

代价：结果页需要同时接收图片地址与解码状态两个参数。
